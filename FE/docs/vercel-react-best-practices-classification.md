# Vercel `react-best-practices` — Classification Against This Repo

Source evaluated: [`github.com/vercel-labs/agent-skills`](https://github.com/vercel-labs/agent-skills),
`skills/react-best-practices/SKILL.md` — 70 rules across 8 priority categories. Rule names/
descriptions below are copied verbatim from that file (fetched directly, not guessed); none
are fabricated.

**Purpose of this file:** reasoning-traceability for why each rule was or wasn't adopted —
**not** a second rulebook. Anything actually enforced already lives in `eslint.config.js`,
`doctor.config.ts`, or `.size-limit.js`; this file just explains the decision. See
`AGENTS.md`'s pointer to this file.

**Stack context that drives most of the Skip calls below:** this is a Vite **SPA** (client-
rendered only — `AGENTS.md` § Tech Stack: "Build: Vite (SPA, not SSR)"). There is no Next.js,
no React Server Components, no server actions, no API routes, and no SWR (TanStack Query is
the server-state library). A large fraction of the 70 rules assume one of those and simply
have no target in this codebase.

## Categories used

| Category            | Meaning                                                                                                                                                                                                                                                                         |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Enforce**         | Adopted as a blocking check (an ESLint rule enabled below), because it is objective, stable, machine-verifiable, low-false-positive, and adds non-overlapping value.                                                                                                            |
| **Skill-guidance**  | Context-sensitive judgment call a linter can't reliably enforce; worth an agent knowing about, not worth blocking on.                                                                                                                                                           |
| **Already-covered** | An existing tool/config in this repo already enforces or structurally satisfies the rule's intent. Tool cited.                                                                                                                                                                  |
| **Skip**            | Not applicable to this stack, too speculative for a domain-agnostic starter, or explicitly out of scope per this repo's own issue history (see AGENTS.md § Performance Budget: "no `React.memo()`/`useMemo()` mandates... speculative runtime micro-optimization enforcement"). |

| `async-defer-await`                  | Skill-guidance  | Same — "move await into the branch that uses it" is a review-time refactor, not a pattern with one canonical AST shape.                                                                                                                                                                                                                                                                                                                                                                                                                               |

## What changed in this repo as a result

**Enforced (1 new ESLint rule):**

```js
// eslint.config.js, inside the shared TS/TSX rules block
'react/jsx-no-leaked-render': 'error',
```

- Maps to `rendering-conditional-render`.
- Comes from `eslint-plugin-react`, already a project dependency — no new package added.
- Flags `condition && <Jsx/>` in a `{}` expression container when `condition` isn't already
  a boolean-safe expression (a literal boolean, a `!`/comparison/call result) — the exact
  shape that can leak a rendered `0`/`NaN`/string when the condition's real type isn't
  boolean. Default `validStrategies: ['ternary', 'coerce']` means both `cond ? <X/> : null`
  and `!!cond && <X/>` remain valid — no new style is forced beyond removing the ambiguous
  form.
- **Negative-fixture proof:** a scratch file with `{count && <span>{count}</span>}` (where
  `count: number`) was linted, confirmed to fail with
  `react/jsx-no-leaked-render` (exit code 1), then deleted.
- **Full-repo run:** `pnpm eslint . --fix` found and safely autofixed 16 real call sites
  across `src/components/auth/*.tsx`, `src/components/common/{ConfirmDialog,EmptyState,
ErrorState,FormField,Input,Toaster}.tsx`, `src/components/example/ExampleWidget.tsx`, and
  `src/components/layouts/RoleLayout.tsx` — all genuine matches of the pattern (error/hint/
  title/description conditionals), not false positives (the rule is purely syntactic and
  only fires on the exact ambiguous shape). `pnpm format:fix` cleaned up the autofixer's
  raw indentation. `pnpm check:lint` and `pnpm check:test` both pass after the change (26/26
  tests green, 0 lint errors).
- `check:lint-contract`'s asserted rule list (`scripts/checks/lint-config-contract.mjs`)
  does not reference this rule, so no update needed there.

**Not enforced, no code changes:** everything else. See tables above.

content duplicated there.
