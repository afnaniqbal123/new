Two ways in, one quality gate

Start a new service from this boilerplate, or add its conventions and enforcement to a codebase you have been shipping from for months. Both paths end with the same six-stage gate running on every commit. Once you have a repo, Quickstart takes over.

A new service

The wizard copies the boilerplate, then strips out what you did not tick. Removal touches five places at once, which is the part that goes wrong when people do it by hand.

Get the template

Clone it under the name you want, then convert the clone in place:

git clone https://github.com/Gok-boilerplates/nestjs-backend.git my-api
cd my-api
node scripts/setup.mjs --in-place

Or skip cloning entirely — this fetches the template into a temp folder, runs the wizard, and deletes itself:

bash <(gh api repos/Gok-boilerplates/nestjs-backend/contents/create.sh \
  -H "Accept: application/vnd.github.raw") my-api

Use bash <(…), never … | bash

Piping makes the script itself stdin, so the wizard's prompts read end-of-file and it silently answers with defaults. You get a project you did not choose, with no error to explain it.

Pick your modules

Arrow keys to move, space to toggle, enter to accept. The first five are locked — the cursor skips them.

  Which modules do you want?
  ↑↓ move · space toggle · enter accept

    ◉ auth                JWT access/refresh, OTP, password reset  (always included)
    ◉ user                User accounts and profile management     (always included)
    ◉ authorization       CASL policies and permission guards      (always included)
    ◉ email               Transactional email + Handlebars         (always included)
    ◉ media               S3 upload/download and presigned URLs    (always included)

  › ◉ stripe              Stripe — cards, invoices, payments, subscriptions
    ○ paypal              PayPal — invoices, payments, subscriptions
    ◉ notifications       In-app notifications (feed, read state)
    ○ chat                Realtime chat (Socket.IO gateway, rooms)
    ○ onesignal           Push notifications via OneSignal
    ○ platform-assistant  AI assistant (OpenAI, conversation store)

Pick how it sends email

A radio, not a checkbox — EMAIL_PROVIDER activates one at runtime, so keeping two only means carrying an SDK the project never calls.

  How should this project send email?
  ↑↓ move · enter accept

  › ◉ brevo     Brevo — the default; one API key (EMAIL_API_KEY)
    ○ ses       AWS SES — reuses your AWS_* credentials; sender must be verified
    ○ sendgrid  SendGrid — SENDGRID_API_KEY, with its own sender override

Know what you want already? Skip both screens: --modules=stripe,chat --email=ses --yes. Or see the plan without writing anything: --dry-run.

Install and run

git remote set-url origin <your-new-repo>
pnpm install            # writes a fresh lockfile — commit it
cp .env.example .env    # then fill in the values
pnpm run verify
pnpm dev

The lockfile is deliberately removed

When modules are dropped it still pins the packages that went with them, and CI runs pnpm install --frozen-lockfile, which rejects a mismatch rather than reconciling it. The first install writes a correct one.

Fill in at least MONGODB_URI and JWT_SECRET. A secret under 32 characters is rejected at startup, on purpose.

Dropping a module is not just deleting a folder

It removes the folder, its #region block in app.module.ts, its keys in config.constant.ts and .env.example, its half of the seed script, and its npm dependencies. Those last four are the ones missed by hand. Choosing an email provider does the same to the other two implementations, SDKs included.

A project you already have

Nothing you have shipped starts failing. Existing violations are recorded in two baseline files, so the rules bind new code only — and the whole export is undone by one git command.

Start from a clean tree

cd ~/work/your-project
git status          # must be clean — the script refuses otherwise

That refusal is the safety story: with a clean tree, git checkout . && git clean -fd puts everything back exactly.

Run the installer

gh api -H "Accept: application/vnd.github.raw" \
  repos/Gok-boilerplates/nestjs-backend/contents/scripts/install-toolkit.sh | sh

Here | sh is correct — this script asks nothing. Only the new-project wizard needs bash <(…).

Your ESLint config is never rewritten

It is kept verbatim as eslint.config.project.mjs, and the new eslint.config.mjs spreads it and appends the 24 custom rules on top. Nothing of yours is parsed or edited.

Install and wire up the hooks

npm install
npx husky            # husky 8 needs `husky install` instead

Use whichever package manager your project already uses — the installer detects it and prints the matching commands, including the right husky invocation for the version you have.

Record what is already there

npm run architecture:accept
npm run lint:baseline

This step is not optional

Skip it and a codebase with months of history opens with hundreds of errors and no way to commit. Those are real numbers from a three-month-old project: 163 architecture violations and 209 lint violations, recorded and forgiven in about two seconds.

architecture:accept, not architecture:baseline

The plain baseline command refuses to record violations it has not seen before — which is the behaviour you want every day after today, and exactly wrong on the first run, when everything is new to it.

Check the gate — and check the rules actually fire

npm run verify
npm run debt         # the recorded debt, by rule

If debt lists no nestjs/* rules, stop

It means the rules were copied but never loaded — the gate would report green while enforcing nothing, which is the one failure here that looks exactly like success.

Changed your mind? git checkout . && git clean -fd removes every trace. Re-running the installer later is safe too: files that already exist are left alone, and only what is missing is added.

The six stages

Both paths end here. npm run verify runs the same six stages the pre-commit hook does, across the whole repo instead of just the staged files.

#StageWhat it checks
01Guard railsSecrets, large files, anything that should never be committed
02Lint & conventionsFormatting plus 24 custom rules that encode this repo's conventions
03Type safetyA full tsc --noEmit, not just the changed files
04Structure & namingNew files land where the module map says they belong
05Architecture boundariesModule cycles, cross-module reads, provider SDK leakage
06DocumentationLinks resolve, ADRs are named and structured, the index is complete

Blocked by it?

claude "/fix-commit" reads the failure and fixes the cause. Both baseline files may shrink and never grow — that is what stops today's exception becoming tomorrow's convention.

When it goes wrong

Each of these came out of a real adoption. Search this page for the message your terminal printed.

163 violation(s) are not in the baseline

You ran architecture:baseline on a project that has never been baselined. That command deliberately will not record violations it has not seen before. On the first adoption run architecture:accept instead.

Invalid option '--suppress-all'

Your ESLint predates 9.24, where suppressions landed. The installer warns about this, but if you got here anyway: upgrade ESLint, then re-run lint:baseline.

No files matching the pattern "test/**/*.ts"

An older copy of the toolkit assumed every project has a test/ directory. Re-run the installer; the lint scripts now glob only the roots that exist.

ERR_PNPM_IGNORED_BUILDS

A dependency wants to run an install script and nothing has ruled on it. pnpm approve-builds answers it for your machine — but record the answer in pnpm-workspace.yaml under allowBuilds and commit it, so the next person is not asked again.

husky - Usage: husky install [dir]

You ran the husky 9 command on husky 8. Before v9 the command is husky install. The hooks stay off silently until it runs, so check .husky/_ exists afterwards.

Skipped · scripts/hooks (exists) — but the folder is empty

git clean -fd can leave a directory behind after removing its files, and an older installer treated an empty directory as already done. The current one merges directories file by file. On an older copy, delete the empty directories with rm -rf first — git clean will not, because git does not track empty directories.

The wizard never asked anything

You piped the bootstrap into a shell. Use bash <(gh api …) instead of gh api … | bash.

Cannot find module '…/dist/main' — after a clean compile

A stale TypeScript build cache. nest start wipes dist/, and a cache living outside it survives, reports everything as already emitted, and leaves the folder empty. Fixed in the boilerplate by keeping the cache inside dist/; on an older copy, rm -f tsconfig.build.tsbuildinfo.

Two lockfiles in the repo

Running a package manager the project does not use leaves its lockfile behind, and then whichever one you invoke decides the dependency tree. Two developers can install different versions and neither will notice. Pick one, delete the other, commit the deletion.

Adopting into an existing project?

.claude/skills/best-practices/ describes this boilerplate, not your codebase. Read it and edit it to match what your project actually does — a skill that describes the wrong conventions is worse than none.
