The skills this repo ships, and when each one fires

Nineteen Claude Code skills live in .claude/skills/ and are committed to git — clone the repo and you have all of them, no plugin install. Four were written for this backend; fourteen are a vendored engineering pack; one is standalone. Four hooks fire them automatically.

Orientation

How skills work

A skill is a folder holding a SKILL.md — instructions Claude loads when the work matches. Two ways one runs:

TriggerHowApplies to
AutomaticClaude reads the skill's description and loads it when your request matches. You say "debug this failing test" and diagnosing-bugs fires on its own.13 skills
Manual onlyThe skill sets disable-model-invocation: true, so Claude will never reach for it by itself. You type /name.6 skills

The six manual-only ones are ask-matt, grill-with-docs, implement, improve-codebase-architecture, setup-matt-pocock-skills and wayfinder — each starts a long, opinionated process you should choose deliberately rather than have chosen for you.

You do not need to memorise any of this

Type / in Claude Code to see the list, or just describe what you want in plain English. The right skill loads itself. This page is for when you want to know what is available and why it behaves the way it does.

Written for this repo4 skills

Built for this backend

These encode decisions specific to this NestJS + Mongoose codebase. They are the ones that would not make sense in another repo.

best-practices

automost important

Our coding conventions — how Nest modules, controllers, services, DTOs, guards and Mongoose schemas are structured here. This is the document the 15 custom ESLint rules encode.

Fires: automatically, any time Claude writes, reviews or refactors backend code. You never call it directly.

architecture-documentation

automandatory

The single workflow for architecture docs and ADRs — where a document goes, whether a decision needs an ADR, whether a diagram earns its place. Adapted from an upstream command with its format menu removed: the upstream offers a choice between C4, Arc42, PlantUML, Structurizr and Draw.io, and offering that choice to an agent is exactly the drift this skill exists to prevent.

Fires: automatically when a change alters module ownership or boundaries, the auth or authorization model, persistence, an external integration, or a cross-cutting convention. Mandatory per CLAUDE.md — docs update in the same PR, not a follow-up.

Most changes are not architectural, and the skill's first question lets you out quickly.

/architecture-documentation

fix-commit

auto

Fixes whatever blocked a commit — lint, type errors, convention violations, secret detection, structure failures, or a rejected commit message. It fixes the root cause and never bypasses the gate. Also pays down baselined convention debt with --debt.

Use it: right after a commit gets blocked.

/fix-commit
/fix-commit --debt nestjs/no-raw-http-exception   # pay down one rule

fe-api-guide

auto

Generates a frontend-integration package from this backend: one consolidated Markdown API guide, a README per module, and a self-contained interactive HTML demo app covering every module and flow — real uploads, real checkout redirects, not JSON dumps.

Use it: when the frontend team needs to know how to call the endpoints. Its output already exists at docs/fe-api-guide.md and docs/fe-demo-app.html.

/fe-api-guide

General engineering skills

Vendored from mattpocock/skills and trimmed to what helps with backend work — prototype and wizard were dropped as UI/infra-focused. Versions are pinned in skills-lock.json.

Building

tdd

auto

Red → green → refactor. The reference for what a good test is, where tests go, the anti-patterns, and the rules of the loop.

/tdd add a rate limiter to the login endpoint

implement

manual only

Takes an agreed spec or set of tickets and builds it, without re-litigating the design. Uses /tdd at pre-agreed seams.

/implement ticket #42

diagnosing-bugs

auto

A structured debugging loop instead of guess-and-check — form a hypothesis, test it, narrow the cause. Skip phases only when explicitly justified.

/diagnosing-bugs the /orders endpoint returns 500 intermittently under load

resolving-merge-conflicts

auto

Works through an in-progress merge or rebase. Finds the primary source for each conflict — commit messages, PRs, issues — preserves both intents where possible, and always resolves; never --abort.

/resolving-merge-conflicts

Thinking it through first

grilling

auto

Interviews you in rounds. Maps the design as a tree of decisions and asks every currently-answerable question in one batch — numbered, each with its recommended answer — then waits. It looks up facts about the codebase itself rather than asking you.

Use it: the closest thing here to "brainstorm with me". Claude often reaches for it when you say "let's build X".

/grilling I want to add a reviews-and-ratings feature to user profiles

grill-with-docs

manual only

grilling + domain-modeling — the same interview, but it writes the outcome up as an ADR and glossary entries as it goes.

Use it: before something big and irreversible. Cheaper to find the flaw now than after it is built.

/grill-with-docs I'm planning to move refresh tokens from cookies to headers

wayfinder

manual only

For work too big for one agent session and wrapped in fog. Charts a shared map issue with child decision tickets and real blocking edges on GitHub, then resolves them one at a time until the route is clear.

Reach for it not when work is merely big, but when making an issue implementation-ready would mean guessing a decision nobody has made. If ownership and acceptance criteria are already clear, use a normal issue. Full guide: docs/guides/wayfinder.md.

/wayfinder plan the migration off the legacy email service

research

auto

Spins up a background agent so you keep working. It investigates against primary sources — official docs, RFCs, source code — and saves findings as a Markdown file in the repo, citing each claim.

Use it: questions where a wrong guess is expensive.

/research the correct way to handle idempotency keys with Stripe webhooks

Design and vocabulary

codebase-design

auto

Shared vocabulary for deep modules — a lot of behaviour behind a small interface, placed at a clean seam. Helps decide where a boundary goes or how to make a service testable.

/codebase-design our NotificationsService interface feels leaky

improve-codebase-architecture

manual only

Scans for deepening opportunities, presents them as a visual HTML report, then grills through whichever one you pick.

Use it: a periodic architecture health check, or onboarding onto unfamiliar code.

/improve-codebase-architecture scan src/modules

domain-modeling

auto

Actively builds and sharpens the project's domain model — challenging terms, inventing edge cases, writing the glossary and ADRs the moment they crystallise. Note this is the active discipline: merely reading CONTEXT.md for vocabulary is not this skill.

/domain-modeling what do we mean by "workspace" vs "organization"?

Review and routing

code-review

autoalso hook-driven

Reviews changes since a fixed point on two axes at once, in parallel sub-agents so neither pollutes the other's context: Standards (does it follow our documented conventions?) and Spec (does it do what the ticket asked?). Reported side by side, never merged or reranked — because a change can pass one axis and fail the other.

Fires on its own too — see the Stop hook below.

/code-review since main

ask-matt

manual only

A router over the other skills. Describe your situation and it tells you which one fits, and which flow — the path through several skills — you are on.

/ask-matt I have a huge messy feature to build, not sure where to start

setup-matt-pocock-skills

manual only

Generated the files in docs/agents/ — issue tracker config, triage labels, domain doc layout — and the skill list in the team guide. Only needed again if the issue tracker changes.

/setup-matt-pocock-skills

Security audit

security-audit

autoundocumented in the team guide

An eight-stage pipeline: fingerprint the stack, research current vulnerability classes and CVEs for what it finds, deep static and data-flow audit, propose a remediation plan, get explicit approval before any code changes, implement, write red-team-style regression tests proving each fix works, then report.

Each stage writes a file, so the process is resumable and you can inspect or override any step — deliberately not a black box that returns a verdict.

Fires on: "audit", "pen-test", "security review", "harden", "find vulnerabilities in" — and narrower asks that are really one stage of it, like "check my dependencies for known CVEs".

/security-audit

This one is missing from the team guide

docs/agents/skills-guide.md does not mention security-audit at all, so nobody reading the guide knows it exists. Given the repo's open debt register, it is arguably the most useful skill here.

Configured in .claude/settings.json. These run without you asking, and one of them can block Claude from ending its turn.

EventScriptDoes
UserPromptSubmitclaude-skill-router.mjsInjects a reminder pointing at the right skill for what you just asked — the nudge that keeps conventions applied proactively rather than fixed at commit time.
PostToolUse

Write | Edit		claude-typecheck-on-edit.mjsTypechecks after each edit, so a type error surfaces in seconds rather than at commit.

The auto-review hook, specifically

It measures how much of src/** changed and forces code-review to run before Claude can finish. It triggers when:

  • a new module folder appears, or
  • 3 or more src/**.ts files changed, or
  • 150 or more lines changed.

Small fixes are left alone. It picks the fixed point itself — merge-base with main on a branch, origin/main or the working tree on main — and will not re-fire on a change set it has already reviewed.

CLAUDE_SKIP_AUTO_REVIEW=1   # turn it off for a session

Separate from the git hooks

These four are Claude Code hooks. The six-stage commit gate is a different mechanism — Husky git hooks in .husky/ running scripts/hooks/pre-commit.mjs, commit-msg.mjs and post-commit.mjs. Those fire for everyone, agent or human. See the Quickstart page.

Conflict handling

If you have the plugin versions installed globally, two copies of the same skill compete and whichever fires is a coin flip — meaning you and your teammates get different behaviour from the same prompt. .claude/settings.json settles it by switching off the global copies so the repo's committed versions always win.

"skillOverrides": {
  "mattpocock-skills:tdd": "off",
  "mattpocock-skills:code-review": "off",
  // … 17 more, plus prototype and wizard which we do not vendor
  "superpowers:brainstorming": "off"
}

Why brainstorming is switched off

The Superpowers plugin ships a brainstorming skill covering the same ground as grilling. This repo keeps grilling because it feeds the rest of the chain and writes its output to a GitHub issue or an ADR, whereas brainstorming ends by handing off to a writing-plans skill this repo does not have, and writes to its own folder.

The honest trade-off, recorded in the team guide: brainstorming sized the ceremony to the job, treating a quick feasibility check differently from a new subsystem. grilling has one gear. In practice a small change has a small decision tree so it wraps up fast — but if it starts interviewing you about a one-line fix, just tell it to get on with it.
