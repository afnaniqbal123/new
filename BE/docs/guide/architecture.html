How this backend is put together, and why

Which module owns what, which dependencies are allowed, how a request proves who it is and what it may then do — plus an honest register of everything currently wrong with it. Two questions this page exists to answer before any code is written: who owns this behaviour, and what may it depend on.

C4 level 1

System context

A REST API plus a WebSocket gateway over MongoDB. One process, one database. It is a boilerplate, so modules are meant to be deleted as often as extended — which is exactly why the boundaries below are enforced mechanically rather than by convention.

C4 levels 2–3

Who owns what

For each module: what belongs to it, what deliberately does not, and what it exposes. If two modules both look like the owner, the owner is the one that would have to change if the rule changed.

auth

businessthe security boundary

Credentials, identity, and access decisions.

Owns
The Passport strategy, the global access guard, @Public(), @TenantScoped() and OrganizationAccessGuard, access-token signing, refresh sessions, password-reset credentials, OTP issue and verify, and the request-context decorators (@GetUser, @GetOrganizationId).
Does not own
The user record. Auth reads the User model for credential checks and membership, but profile CRUD, roles-as-data and account lifecycle belong next door.
Exposes
AuthService, TokenService, RefreshTokenService, PasswordResetService, JwtStrategy, OrganizationAccessGuard — plus guards and decorators imported directly by path.

authorization

business@Global

What an identified caller may do.

Owns
The permissions mechanism: ability construction, the @RequirePermissions route guard, record-level assertions, and the registry policies register with.
Does not own
Any rule. Policies live in the module that owns the data. It carries no domain vocabulary at all — AuthorizationContext.principal.role is a string, not USER_ROLES.
Exposes
PermissionsGuard, AuthorizationService, AbilityFactory, PolicyRegistry, @RequirePermissions, @GetAbility, Action.

user

businessreference module

The account record. Copy how this one does things.

Owns
The User schema, profile CRUD, avatar handling, the email-change flow, and the role value stored on an account. Also the rules about user records — policies/user.policy.ts, the reference policy.
Does not own
How a caller proves who they are, or the permissions mechanism. It applies PermissionsGuard and OrganizationAccessGuard without implementing either.
Exposes
UserService.

chat

business
Owns
Chat rooms, messages, unread counts, and the WebSocket gateway.
Does not own
User identity — though it does query the User collection directly for participant validation and search, a documented cross-module read tracked as debt.
Exposes
Focused services — ChatRoomService, ChatMessageService, ChatUnreadService — not one general-purpose ChatService.

notifications

business
Owns
Notification records, per-user read state, and the SSE stream.
Does not own
Push delivery (onesignal) or email delivery (email).
Exposes
NotificationService, NotificationReadService, NotificationStreamService.

email

support
Owns
Provider selection, Handlebars templates, and sending.
Does not own
When an email is sent or what it says domain-wise — the calling module decides that and passes the data.

Does not own

Each is a thin base module exporting the SDK client, plus sub-feature modules — payment, subscription, invoice, webhook.

Security model

Request lifecycle

What happens between the socket and your handler, in order.

#StepComponentReads DB
1Is this route @Public()? If so, straight to the handlerJwtAccessGuardno
2Verify signature, expiry, HS256, issuer, audienceJwtStrategyno
3Check type === SIGNIN_TOKEN and that sub, email and a known role are presentisAccessTokenClaimsno
4Attach the AuthenticatedPrincipal to request.userJwtStrategyno
5On @TenantScoped() routes only: confirm membership of the asserted organizationOrganizationAccessGuardyes
6Compose every registered policy into one ability for this callerAbilityFactoryno
7Test @RequirePermissions against it — 403 if unsatisfiedPermissionsGuardno
8Strip undeclared properties, validate the DTOCustomValidationPipeno
9Handler runs; the service loads the record and calls assertCan on ityour serviceyes

No step in 1–8 reads the user collection, apart from the tenant guard on routes that explicitly ask for it. That is the design, and it is asserted by a test rather than merely intended.

Security model

Authentication

Authentication is on by default. A new controller needs no guard to be protected; it needs @Public() to not be.

The authenticated principal

JwtStrategy.validate() is the only producer of this shape. Everything downstream reads it and nothing else.

type AuthenticatedPrincipal = {
  id: string;
  email: string;
  role: USER_ROLES;
  sessionId?: string;
};

Access tokens

15-minute TTL, HS256. Every claim below is checked, not merely present.

{
  "sub": "507f1f77bcf86cd799439011",
  "email": "user@example.com",
  "role": "ADMIN",
  "type": "SIGNIN_TOKEN",
  "sid": "507f1f77bcf86cd799439099",
  "iss": "nestjs-backend",
  "aud": "nestjs-api",
  "exp": 1234567890
}

Encoded, not encrypted

Anyone holding the token can read every claim. Only what the authorization boundary actually consumes goes in — never anything else.

Sessions and rotation

What revokes what

EventEffect
LogoutRevokes the session named by sid. A token carrying no sid revokes every session, rather than reporting success having revoked nothing.
Logout all devicesEvery session for the user.
Password changeEvery session, plus outstanding reset links and unredeemed OTPs of both kinds.
Password resetSame as password change.
Suspended / deletedRefresh refused and remaining sessions revoked at the next attempt.
Rotated token reusedEvery session for the user.

Password reset — two deliberate omissions

  • It does not accept an email. VerifyResetPasswordDto has no such field, and the global whitelist: true pipe strips one if sent. The account comes from the consumed record, so the credential and the identity it authorizes come from the same place.
  • It does not put the token in a JWT. Single-use is server-side state; a JWT cannot be un-issued.

Never log a raw reset token or a full reset URL

Either one is a working password reset for that account.

Tenancy

x-organization-id is an assertion by the caller, not a fact. Two request properties keep that distinction visible:

PropertyMeaning
request.requestedOrganizationIdWhat they asked for. Untrusted.
request.organizationIdWhat they were found entitled to. Written only by OrganizationAccessGuard, read only via @GetOrganizationId().

Without the guard, @GetOrganizationId() returns 403 rather than undefined. An empty tenant filter turns "scoped to my organization" into "scoped to everything", so failing is the safe answer.

Security model

Authorization

Authentication answers who; this answers what. CASL is the engine (ADR 0003), and the split that matters is this: the authorization module owns the mechanism and none of the rules. Policies live in the module that owns the data and register themselves, so the authorization module never learns which domain modules exist — and adding a feature never means editing it.

Vocabulary

TermMeaning
ActionManage, Create, Read, Update, Delete, List. Manage is CASL's wildcard.
SubjectA name such as 'User', declared by the module that owns the data — or a record tagged with one via subject().
AbilityThe composed rule set for one caller, built per request, attached to request.ability, read with @GetAbility().

List is separate from Read because callers who may browse a directory often may not open an arbitrary entry — exactly the split this codebase already had between GET /users/all and GET /users/:id.

Two stages, and why both are required

This is not defence in depth. It is one mechanism with a hole the second stage exists to close.

Field-level rules

A grant can name the fields it covers. Without this, "edit your own profile" also means "make yourself an OWNER" — the record check passes because the record is theirs, and an unfiltered DTO carries role straight through.

can(Action.Update, USER_SUBJECT, ['name', 'phone'], { _id: principal.id });

Callers pass the fields they are writing to assertCan, which refuses if any falls outside the grant. A grant with no field list covers every field, so field checks are inert until a policy narrows one.

Guard ordering — the mistake that fails silently

Nest only respects ordering within a single @UseGuards

Controller-level guards run before route-level ones. A tenant guard applied per route therefore runs after PermissionsGuard, and the ability gets built with organizationId: undefined — every tenant-conditioned rule quietly evaluating against nothing. Declare both at controller level, in order:

@UseGuards(OrganizationAccessGuard, PermissionsGuard)
export class UserController {
  @Get('all')
  @TenantScoped()          // the tenant guard stands aside without this
  @RequirePermissions({ action: Action.List, subject: USER_SUBJECT })

Statelessness, and what it costs

PermissionsGuard reads nothing from the database — abilities are built from token claims and already-authorized tenant context. Stated plainly: a role change takes effect when the caller's current access token expires, up to 15 minutes later. Anything needing immediate effect must revoke the refresh sessions and accept the same bounded window.

Tenant membership is the deliberate exception. It is per-user mutable state a short-lived token cannot speak for, so the guard reads it — separately, after identity is settled, and only on @TenantScoped() routes.

401 versus 403

  • 401 — no identity, or an untrustworthy one. Re-authenticating may help.
  • 403 — identity established, action not permitted. Re-authenticating cannot help.

Every refusal returns the same message whatever the caller lacked. Naming the missing permission tells someone probing the API which door to try next.

Forbidden patterns

Do notInstead
Add a role guard for business rulesWrite a policy
Put @Roles(...) on a new route@RequirePermissions(...)
Check roles inside a serviceTake an AppAbility and assertCan
Read the database in a policy or guardPut the claim in the token, or check after loading
Pass a request into a service for authorizationPass the AppAbility
Use a raw x-organization-id in a policyUse context.organizationId

Policies must be pure — read the context, add rules, return. PermissionsGuard runs every policy on every guarded request, so a policy that awaits something makes authorization as slow as its slowest rule.

@Roles and RolesGuard are deprecated but retained so an adopter's existing routes keep working. Nothing in src/ still applies them.

The contract

Dependency rules

Nine rules. Violating most of them blocks the commit.

  1. Controllers call services in their own module.A controller may use another module's contract — guards, decorators, DTOs, constants — but not its internals. Reaching for a service or gateway means the boundary is in the wrong place.
  2. Provider SDKs stay in their module.stripe, @aws-sdk/*, @getbrevo/brevo, @onesignal/*, openai, socket.io, jsonwebtoken, bcrypt, otplib are each confined to exactly one module, subpath imports included.
  3. Do not import another module's schema for convenience.Needing another module's data is a signal to call its service. Re-exporting a schema through an intermediate file does not launder it — the check follows export … from '*.schema' too.
  4. Cross-module dependencies express a capability need."I need to send email" — not "that file happened to have what I wanted".
  5. Two modules should not depend on each other.One documented exception exists (auth ↔ user). Adding a second needs an ADR.
  6. forwardRef is not an architecture.It is an escape hatch for a cycle you have decided to keep. Every current use is baselined — in modules and in providers — so the count can fall but not rise unnoticed.
  7. Shared helpers are not a dumping ground.src/utils, src/types, src/constants and src/guards hold dependency-free code and may import no feature module. Anything that only makes sense alongside a module lives in it — which is why @GetUser moved into auth. src/scripts is exempt.
  8. AppModule composes and nothing else.No business providers, no orchestration.
  9. Export the capability, not the internals.A module's exports is its contract. Keep it to what others genuinely need.

The contract

Enforcement

These rules are checked, not merely written down.

pnpm run architecture:check      # stage 5 of `verify`
pnpm run architecture:baseline   # re-record after resolving one; refuses to add
pnpm run architecture:accept     # explicitly accept a documented new exception
pnpm run architecture:test       # the checker's own tests

It reports new module cycles, forbidden cross-module reads, and provider-SDK leakage — with the dependency path that caused each and the direction it expected.

The baseline is keyed by file, not by rule

So a new file cannot inherit an existing exception: modules/auth already reading user.schema.ts does not license the next file to do the same. The list can shrink but never grows on its own. Recording a new exception is a deliberate act — document it here first, then regenerate.

Auth-specific lint rules

Seven rules in tools/eslint-rules/rules/auth.mjs. Each bans a pattern that was real code in this repo before the auth rewrite.

RuleBans
no-direct-jwt-verifyA second token-verification path
no-direct-jwt-signMinting tokens outside TokenService
no-db-in-access-authA model injected into a strategy or access/role guard
no-legacy-auth-guardReferencing the deleted JwtAuthGuard
no-raw-organization-headerReading the tenant header outside its guard
no-manual-bearer-parsingHand-rolled Authorization parsing
one-access-strategyA second Passport JWT strategy

What the rules cannot catch

They are static checks, so they see syntax, not behaviour. Indirection defeats them — re-exporting verify, or taking a reference before calling it. A different JWT library is not in the allow-list of names. And a guard that delegates its lookup to an injected service reads the database without ever naming a model.

That last one is covered behaviourally instead: the authorization e2e asserts the user collection is read zero times across an authenticated request, which fails however the read is spelled. Treat the lint rules as fast feedback and that assertion as the real guarantee.

Security scanning — what runs, and what does not

LayerCatchesStatus
ESLint + nestjs/*Project invariants — auth boundaries, module boundaries, response envelopeactive
Dependabot version updatesOutdated dependenciesactive
Dependabot security alertsDependencies that are vulnerable, not merely oldoff — repo setting
CodeQLSemantic analysis — injection, taint flowblocked

There is no CodeQL workflow on purpose. Code scanning needs GitHub Advanced Security, unavailable for a private repo on a free organisation plan — verified against the API rather than assumed. A workflow committed today would initialise, analyse, then fail at the upload step on every run: a permanently red check teaches people to ignore red checks, which is worse than no workflow. It unblocks if the org changes plan, the repo goes public, or GitHub changes the entitlement.

Security alerts are a separate, account-side switch under Settings → Code security. .github/dependabot.yml configures version updates only — it does not turn alerts on.

Honest register

Known exceptions and debt

Listed so they read as decisions, not as patterns to copy. One is accepted; the rest are debt, and two are live security holes.

accepted settled, do not "fix"   debt wants an issue   known hole security-relevant

01

auth ↔ user is a permitted cycle

accepted

auth needs the User model and USER_ROLES; user needs the guards, decorators and password hashing. The two are mutually defining — credentials without an account record mean nothing.

Do not "fix" it with more forwardRef. If it is ever broken, that is an ADR.

02

AuthModule and UserModule each declare UserService

debt

Rather than importing UserModule, both list UserService (and MediaService, EmailService) in providers. Nest therefore builds separate instances — harmless while these services are stateless, wrong the moment one caches anything.

The fix is a one-directional import once the cycle above is resolved.

03

Payment and chat schemas reference the User schema directly

debt

stripe/card, stripe/subscription, paypal/subscription and chat import User to declare ref relationships — a Mongoose idiom rather than a business dependency. Baselined per file. The fix is a shared ref constant so the schema type is not the coupling point.

04

chat reads the User collection directly

debt

It queries users for participant validation and search rather than calling UserService. Narrow and deliberate, and baselined so it cannot spread.

05

Clearing emailVerified leaves no way to re-verify

debt

UserService.changeEmail and update both set emailVerified: false when the address changes but leave status as ACTIVE. Signup verification is the only path that sets it true, and it refuses anything not PENDING — so once an active user changes their address, the flag stays false with no route back.

Harmless today because nothing gates on it for an active account. It becomes a live bug the moment something does. Wants either a re-verification flow or a decision that the flag means nothing after signup.

06

POST /users and GET /users carry no permission at all

debtmost serious of the debts

Neither route has ever had a role or permission check — any authenticated caller may create a user or list every user. The CASL migration preserved behaviour rather than changing it, so they are still open. Confirmed in user.controller.ts: the guarded routes carry @RequirePermissions; these two do not.

Adding it is a small change with a real behaviour impact, so it wants its own issue and its own review.

07

Payment controllers resolve the user from the request payload

debt

Stripe and PayPal handlers take the user from the body instead of the authenticated principal. They are authenticated — the global guard covers them — but they should read @GetUser.

08

The notifications SSE stream identifies its subscriber by route param

known hole

EventSource cannot send an Authorization header, so the stream is @Public() and trusts :userId. The fix is a short-lived stream ticket minted by an authenticated endpoint.

09

ChatGateway trusts a client-supplied userId

known hole

The WebSocket handshake performs no verification whatsoever. Flagged in the gateway itself. Must be closed before production.

10

Most modules answer errors with HTTP 200

debtlargest remaining

Outside auth, a failure returns SerializeHttpResponse(null, 4xx, …) — an envelope carrying the status in its body while the response itself is 200. Auth was converted to real status codes; chat, notifications, Stripe and PayPal were not, because that refactor explicitly required preserving HTTP contracts.

It means a client cannot rely on the HTTP status anywhere but auth. Converting it is a breaking change for every consumer and wants its own issue.

A numbering bug in the source doc

docs/architecture/module-architecture.md numbers two different items 8, so the list reads as nine entries when there are ten. The register above is renumbered 01–10.

Honest register

Deliberately absent

Noted so their absence reads as a decision rather than an oversight. Adding any of them is an ADR.

Not hereWhy
API gateway, service mesh, queueOne process, one database.
Caching layerAuthentication needs none by design; nothing else has needed one yet.
Multi-region or replication strategyDeployment is left to the project that adopts this kit.
Hexagonal / DDD / CQRS / repository layerThe architecture documents and constrains the module structure that exists. It does not mandate a folder migration.
