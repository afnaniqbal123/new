# Architecture — Structure, Modules, Imports & Types

## Project Structure

This project is generated by the `framegen` CLI from `templates/nestjs/`,
which is split into a `base/` (always present, framework-agnostic of which
feature modules were picked) and one folder per feature module under
`modules/`. Cross-cutting code that only makes sense alongside a specific
module (e.g. `RolesGuard` needs auth, `user.constant.ts` needs the user
module) travels **with that module** instead of sitting in a generic `src/`
folder — this repo may not have all 9 modules present, depending on what was
selected at generation time.

### Rules

- **Generic cross-cutting concerns** — code with no dependency on any one
  feature module (`guards/validation.ts`, `types/common.ts`,
  `types/templates.type.ts`, `utils/serializer.ts`,
  `constants/config.constant.ts`, `constants/notification.ts`,
  `constants/api-response/general.response.ts`) — live directly under `src/`
  and are present in every generated project regardless of module selection.
  These folders import from no feature module, and the `shared-folder-purity`
  architecture rule keeps it that way. `@GetUser` and `@GetOrganizationId`
  used to sit here; they now live in `modules/auth`, which owns the request
  context they read.
- **Module-owned cross-cutting concerns** — anything that only compiles or
  makes sense when a specific module is present (auth guards/strategies/
  decorators that need the `User` model, module-specific constants and
  `api-response` enums) — live inside the module that owns them, per the
  table above, not in a shared `src/` folder. `auth`, `user`, and `media`
  are almost always present together (see the dependency graph the CLI
  resolves at generation time), so code in `modules/auth/` may freely import
  from `modules/user/` and vice versa.
- **Feature-specific constants** (route paths, error messages, event names)
  live inside the module under `constants/`.
- Every feature module must have its own `README.md` documenting its purpose
  and public API.
- Test files that are unit tests sit **next to** the file they test
  (`*.spec.ts`); E2E tests live exclusively in `test/`.

## Module Architecture

Every feature module follows the same internal layout:

```
<feature>/
├── <feature>.module.ts
├── <feature>.controller.ts
├── <feature>.service.ts
├── dto/
│   └── <action>.dto.ts
├── schemas/               (if the module owns Mongoose models)
│   └── <entity>.schema.ts
├── enums/                 (if the module owns enums)
│   └── <entity>-<aspect>.enum.ts
├── constants/             (module-scoped strings/events/routes, and any
│                           app-wide constants this module owns — see above)
│   ├── errors.ts
│   ├── success.ts
│   └── routes.ts
├── types/                 (module-scoped types)
└── README.md
```

**Module declaration rules:**

- Register Mongoose models locally with `MongooseModule.forFeature([...])` — never globally.
- `exports` array must only contain providers that other modules actually need.
- Register a new feature module by importing it in `src/app.module.ts`.
- Compound domains (Stripe, PayPal) use a **thin base module** that exports the SDK client service, plus **sub-feature modules** (`payment`, `subscription`, `invoice`, `webhook`) imported through the base module.
- Controllers need no authentication guard and no `User` model registration.
  `JwtAccessGuard` is registered globally via `APP_GUARD` in `AuthModule` and
  authenticates from token claims alone, so there is nothing for a feature
  module to wire up. Register `MongooseModule.forFeature([{ name: User.name,
schema: UserSchema }])` only when the module's own code actually queries
  users — `modules/chat/chat.module.ts` is the remaining example. See
  `docs/architecture/security/authentication.md`.

## Import Paths

**Absolute imports** (preferred for cross-module references):

```typescript
import { CONFIG } from 'src/constants/config.constant';
import { RolesGuard } from 'src/modules/auth/guards/roles.guard';
import { GetUser } from 'src/modules/auth/decorator/user.decorator';
```

**Relative imports** (only for files within the same module folder):

```typescript
import { AuthService } from './auth.service';
import { SignInDto } from './dto/signin.dto';
import { UserService } from '../user/user.service';
```

**Rules:**

- Use `src/...` absolute paths for anything outside the current module folder.
- Use `./` or `../` relative paths only for files within the same or adjacent module.
- No barrel (`index.ts`) files — import the concrete file directly.

## Types

```
src/types/
├── common.ts               # Shared generic types (always present)
└── templates.type.ts       # (always present)

src/modules/auth/types/
├── email.type.ts           # EMAIL_SUBJECT enum and email-related types
└── otp.type.ts             # OTP_TYPE enum
```

- Shared, dependency-free types that cross module boundaries live in `src/types/`.
- Module-specific types (including ones only meaningful alongside a
  particular module, like the auth-related ones above) live in
  `<module>/types/`.
- Prefer `type` aliases over `interface` for plain data shapes; use `interface` when extension or declaration merging is needed.
